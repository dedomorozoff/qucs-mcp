# Qucs-S MCP — дизайн

Дата: 2026-10-24
Статус: на согласовании

## 1. Контекст и цель

Нужен MCP-сервер для opencode, который превращает компактное описание цепи в готовую схему Qucs-S (`.sch`), проверяет её и при необходимости запускает симуляцию. Основной сценарий: агент описывает цепь, MCP собирает файл, пользователь открывает его в Qucs-S и при желании правит руками.

Qucs-S 25.1.1 установлен в `C:\Users\lau\Desktop\Soft\Qucs-S-25.1.1-win64` вместе с ngspice 44.2. GUI-автоматизация не нужна: у `qucs-s.exe` есть headless-режим.

## 2. Что уже проверено на этой установке

- Генерация нетлиста: `qucs-s.exe -n --ngspice -i схема.sch -o схема.cir` работает без GUI.
- Симуляция: `qucs-s.exe -n --ngspice --run -i схема.sch -o схема.dat` считает и пишет Qucs Dataset в `-o`.
- Метки на проводах соединяют цепи по имени, а не только геометрически. Проверено: две разорванные цепочки с меткой `MID` дали в нетлисте `R1 IN MID` и `R2 MID 0`.
- Схема из минимальных секций (`Properties`, `Symbol`, `Components`, `Wires`, `Diagrams`, `Paintings`) валидна.
- `qucs-s.exe --list-entries` отдаёт шаблоны строк для 161 встроенного компонента. Команда падает в конце с `std::bad_alloc`, но полезный вывод успевает записаться; использовать её только при разработке, не в рантайме.
- Полный сквозной прогон RC-фильтра с метками дал `.dat` с переменными `ac.v(in)` и `ac.v(out)`.

## 3. Границы

### Цели

- `create_schematic`: SPICE-подобное описание → валидный `.sch` + отчёт проверки.
- Поддержка базового набора: R, C, L, `S4Q_V`/`S4Q_I`, диод, BJT, MOSFET, GND; анализы `.op`, `.dc`, `.ac`, `.tran`; `.model`, `.param`, `.include`. Пробники — второй этап.
- Детерминированная раскладка по сетке, короткие выводы и метки цепей.
- `validate_schematic`: генерация нетлиста и сравнение с эталоном; без эталона — структурные проверки.
- `simulate_schematic`: запуск через Qucs-S и разбор `.dat` в структурированный ответ.
- `read_schematic`: разбор существующего `.sch` в модель (best effort), чтобы можно было перегенерировать.
- `list_components` / `describe_component`: каталог поддерживаемых компонентов и их выводов.
- Работа на Windows с установленным Qucs-S; пути настраиваются.
- MCP по stdio, регистрация в opencode.

### Не цели (MVP)

- Синтез цепи из естественного языка — это делает агент, MCP принимает уже готовое описание.
- Красивая ортогональная трассировка проводами — второй этап.
- Поддержка всех компонентов Qucs-S и всех библиотек — начинаем с ядра, расширяем каталогом.
- Управление GUI, клики, скриншоты.
- Отрисовка графиков; результаты отдаются данными, графики строит Qucs-S.
- Инкрементальное редактирование существующих схем — в MVP чтение и перегенерация, точечные правки вторым этапом.
- Кроссплатформенность как требование; код держим переносимым, но проверяем на Windows.

### Анти-цели

- Выдать `.sch`, который открывается, но имеет неверные соединения.
- Молча «починить» неподключённый вывод, скрыв проблему.
- Требовать запущенный GUI Qucs-S.
- Менять файлы установки Qucs-S.

## 4. Подход и альтернативы

Рассматривались три варианта:

1. **Каркас с метками цепей — выбран.** Компоненты на сетке, у каждого вывода короткий провод с именем цепи. Qucs-S соединяет одинаковые имена. Любая топология, минимум кода, устойчиво к сдвигу элементов. Схема читается как принципиалка с подписями узлов.
2. **Полная трассировка проводами.** Красивее, но нужен маршрутизатор: пересечения, наложения, точки соединения. Отложено на второй этап; входной формат при этом не меняется.
3. **Шаблоны типовых схем.** Идеальный вид для известных топологий, но не обобщается на произвольные. Оставлено как возможное дополнение.

Выбран вариант 1: он даёт рабочий инструмент для произвольных цепей и проверяемый результат.

## 5. Архитектура

Язык — Go 1.27.3. MCP SDK — официальный `github.com/modelcontextprotocol/go-sdk` v1.8.0. Внешних зависимостей, кроме SDK, нет; всё остальное — стандартная библиотека. На выходе один статический бинарник `qucs-mcp.exe`.

```
SPICE-подобный текст
        │
        ▼
  internal/spice  ──►  internal/model (CircuitSpec)
        │                     │
        │                     ├──► internal/layout (координаты, выводы, метки)
        │                     │
        │                     └──► internal/sch (запись .sch)
        │                                │
        │                                ▼
        │                     internal/validate (qucs-s -n)
        │                                │
        │                                ▼
        │                     internal/runner (qucs-s --run)
        │                                │
        ▼                                ▼
  read_schematic ◄── internal/sch   internal/dataset (.dat)
```

Пакеты:

- `cmd/qucs-mcp/main.go` — точка входа, `mcp.NewServer`, `StdioTransport`.
- `internal/server` — регистрация инструментов, JSON-схемы, обработка ошибок.
- `internal/model` — `CircuitSpec`, `Component`, `Pin`, `Net`, `Analysis`.
- `internal/spice` — парсер SPICE-подмножества, нормализация значений.
- `internal/components` — каталог: шаблоны строк `.sch`, выводы, полярность, поддерживаемые типы.
- `internal/layout` — раскладка, выводы, метки, GND.
- `internal/sch` — запись и чтение `.sch`, сохранение неизвестных секций.
- `internal/netlist` — вызов `qucs-s -n`, разбор SPICE-нетлиста.
- `internal/validate` — сравнение ожидаемых и фактических цепей.
- `internal/dataset` — разбор Qucs Dataset.
- `internal/runner` — `os/exec`, таймауты, пути, ошибки.
- `internal/config` — пути, переменные окружения, настройки.

Сборка: `go build -o bin/qucs-mcp.exe ./cmd/qucs-mcp`. Тесты: `go test ./...`.

## 6. Входной формат

Основной вход — строка в SPICE-подобном синтаксисе. Пример:

```
* RC low-pass
V1 in 0 DC 0 AC 1
R1 in out 1k
C1 out 0 100n
.ac dec 91 10 1MEG
```

Правила:

- Первый символ имени устройства задаёт тип: `R`, `C`, `L`, `V`, `I`, `D`, `Q`, `M`.
- `X` (подсхемы) в MVP не поддерживается: понятная ошибка «subcircuits are phase 2». Это осознанно: иерархия меняет парсер, модель, каталог, раскладку и сравнение цепей.
- Узлы — имена; `0` — земля.
- Строки, начинающиеся с `*`, — комментарии.
- `.model`, `.param`, `.include`, `.op`, `.dc`, `.ac`, `.tran` поддерживаются.
- Независимые источники отображаются в «сырые» компоненты Qucs-S `S4Q_V` / `S4Q_I`. Это закрывает `DC`, `AC`, `DC ... AC ...`, `SIN`, `PULSE`, `PWL` и комбинированные описания одной строкой. Отдельные `Vdc`/`Vac` не нужны.
- `.include` разрешается относительно каталога итогового `.sch`; отсутствующий файл — ошибка на этапе проверки/симуляции, а не создания. Копировать include-файлы не будем.
- Нормализация значений применяется только к голым числовым литералам. Выражения в `{...}`, `.param` и арифметика не переписываются. SPICE `1M` = милли, `1MEG` = мега; на выходе `1m` и `1M`. Отдельный тест.
- Безобидные директивы `.end`, `.title`, `.options`, `.temp` и продолжения строк `+` принимаются; `.end` игнорируется молча, остальные — с предупреждением, если их смысл не переносится.
- Неизвестные устройства и анализы — ошибка с понятным сообщением и списком поддерживаемых.

Дополнительно можно принять структурированный JSON (`components` + `connections` + `analyses`), но в MVP достаточно текста. JSON добавим, если понадобится точное управление координатами.

## 7. Модель цепи

```go
type Pin struct {
    Name string // "1", "2", "+", "-", "c", "b", "e"
    Net  string
}

type Component struct {
    Ref   string            // "R1"
    Type  string            // "R", "S4Q_V", ...
    Value string            // "1k" или сырая SPICE-строка источника
    Pins  map[string]string // имя вывода -> цепь
    Props map[string]string // дополнительные свойства
}

type Analysis struct {
    Type   string            // "ac", "dc", "tran", "op"
    Params map[string]string
}

type CircuitSpec struct {
    Name       string
    Components []Component
    Analyses   []Analysis
    Models     []string
    Params     map[string]string
    Includes   []string
}
```

Модель не хранит координаты. Координаты появляются только на этапе раскладки.

## 8. Каталог компонентов и геометрия выводов

Для каждого поддерживаемого типа хранится:

- шаблон строки `.sch` (взят из `--list-entries` и примеров);
- список выводов с локальными координатами;
- допустимые ориентации (горизонтальная/вертикальная для двухвыводных, фиксированная для остальных);
- полярность (для источников и диодов);
- соответствие SPICE-префиксу.

Предварительная таблица (подлежит калибровке тестами):

| Тип | Выводы (rot=0, mirror=0) | Примечание |
|---|---|---|
| R, C, L | (-30,0), (30,0) | вертикально: (0,-30), (0,30) |
| S4Q_V, S4Q_I | (-30,0), (30,0) | полярность уточнить калибровкой; `S4Q_V` проверен |
| GND | (0,0) | один вывод |
| DIODE_SPICE | (-30,0) анод, (30,0) катод | вертикально: (0,-30), (0,30) |
| _BJT | (0,-30) C, (-30,0) B, (0,30) E | фиксированно |
| _MOSFET | (0,-30) D, (-30,0) G, (0,30) S | сток-исток, подложка на истоке |
| IProbe, VProbe | (-30,0), (30,0) | второй этап, не в MVP |
| Sub, Port | из `.lib` / (0,0) | второй этап, не в MVP |
| SpiceModel, SpicePar, SpiceInclude | нет выводов | текстовые блоки |
| .DC, .AC, .TR, .SW | нет выводов | блоки анализа |

Ориентации в MVP: только `rot=0, mirror=0` (горизонтально) и `rot=0, mirror=1` (вертикально) для двухвыводных; остальные — фиксированно. Общий поворот на произвольный угол не нужен.

Калибровка: тест ставит один компонент в известную точку, прикрепляет к каждому предполагаемому выводу провод с меткой, генерирует нетлист и проверяет, какой узел получила каждая метка. Результат фиксируется в таблице и в тестах. Это защищает от ошибок полярности и сдвига выводов.

## 9. Раскладка

Координаты кратны 10. Базовые константы:

- шаг сетки: 10;
- расстояние между компонентами: 120 по X, 100 по Y;
- длина вывода: 20;
- отступ метки: 5, -10;
- отступ GND: 30.

Алгоритм MVP:

1. Разделить компоненты на группы: источники, последовательные элементы, шунты, полупроводники, земля, анализы, модели.
2. Разместить источники в левой колонке, последовательные элементы — в средней, шунты — ниже, полупроводники — в центре, анализы — внизу.
3. Каждому выводу добавить короткий провод длиной 20 и метку цепи.
4. Для каждого вывода, соединённого с `0`, поставить символ GND и соединить его проводом.
5. Блоки анализов и модели разместить без выводов.
6. Если цепь состоит из одной точки (вывод ни с чем не соединён), всё равно поставить метку и выдать предупреждение.

Так как связи задаются метками, раскладка не влияет на электрику. Это главное свойство выбранного подхода.

## 10. Запись `.sch`

Документ:

```
<Qucs Schematic 25.1.1>
<Properties>
  <View=0,0,1200,900,1,0,0>
  <Grid=10,10,1>
  <DataSet=<name>.dat>
  <DataDisplay=<name>.dpl>
  <OpenDisplay=0>
  <Script=<name>.m>
  <RunScript=0>
  <showFrame=0>
  <FrameText0=Title>
  ...
</Properties>
<Symbol>
</Symbol>
<Components>
  ...
</Components>
<Wires>
  ...
</Wires>
<Diagrams>
</Diagrams>
<Paintings>
</Paintings>
```

Правила:

- Имя файла и имена `.dat`/`.dpl` должны совпадать, иначе Qucs-S предупреждает.
- Строка компонента: `<TYPE REF 1 x y lx ly rot mirror "value" 1 ...>`; число и порядок свойств — из шаблона.
- Строка провода: `<x1 y1 x2 y2 "label" lx ly rot "">`.
- Запись атомарная: сначала временный файл, потом замена.
- Кодировка UTF-8, переводы строк LF (проверено, Qucs-S читает).

## 11. Проверка

`validate_schematic(path, expected_netlist="")` работает в двух режимах:

- **С ожидаемым описанием** (так проверяет `create_schematic`): сравнить фактические цепи с моделью.
- **Без ожидаемого описания** (для произвольного `.sch`): проверить, что нетлист генерируется, собрать фактическую связность из геометрии и меток, найти висящие выводы (цепь с одним выводом, кроме земли), дубли `ref` и неизвестные компоненты. Отличить «неправильную, но самосогласованную» схему без эталона нельзя — это честно указывается в отчёте.

Шаги:

1. Сгенерировать нетлист: `qucs-s.exe -n --ngspice -i out.sch -o out.cir`.
2. Проверить код возврата, наличие файла и отсутствие ошибок в stderr.
3. Разобрать нетлист: строки устройств, узлы по типам.
4. Сопоставить `(ref, pin) → net` с ожидаемой моделью.
5. Ошибки:
   - вывод получил `_netN` вместо именованной цепи — неподключён;
   - две ожидаемо разные цепи слились в одну — короткое замыкание;
   - компонент отсутствует в нетлисте — не распознан.
6. Вернуть отчёт:

```json
{
  "valid": true,
  "pins": [
    {"component": "R1", "pin": "1", "expected": "in", "actual": "in", "ok": true}
  ],
  "errors": [],
  "warnings": []
}
```

Проверка обязательна для `create_schematic` по умолчанию. Если она не прошла, файл всё равно возвращается, но с `valid=false` и отчётом; молчаливого успеха нет.

## 12. Симуляция и результаты

Команда: `qucs-s.exe -n --ngspice --run -i out.sch -o out.dat`, `cwd` — каталог схемы.

- Проверить код возврата, stderr, наличие `.dat` и заголовка `<Qucs Dataset`.
- Разобрать независимые и зависимые переменные, включая комплексные значения.
- Вернуть имена анализов, переменных, количество точек, min/max.
- Полные массивы не отдавать по умолчанию; предусмотреть флаг `include_data` и/или запись CSV.
- Таймаут по умолчанию 60 с, настраивается.

## 13. Чтение существующих схем

- Разобрать `Properties`, `Components`, `Wires`; неизвестные секции сохранить как есть.
- Для известных компонентов восстановить `ref`, `type`, `value`, координаты, ориентацию.
- Восстановить цепи: выводы + концы проводов + метки, объединение через union-find.
- Вернуть модель и/или SPICE-описание.
- При перегенерации сохранять позиции компонентов с теми же `ref`, если это возможно.

## 14. API MCP

Инструменты (Go SDK, имена и сигнатуры):

1. `create_schematic(netlist, name?, output_dir?, base_path?, validate=true, simulate=false, overwrite=false)`
   - возвращает `path`, `netlist_path`, `valid`, `report`, `warnings`, `simulation`.
   - `base_path`: если задан, прочитать существующий `.sch`, сохранить позиции компонентов с теми же `ref` и неизвестные секции, затем перегенерировать. Это и есть «правка существующей схемы» в MVP.
2. `update_schematic(path, netlist, validate=true, simulate=false)` — то же, что `create_schematic` с `base_path=path`; пишет в тот же файл.
3. `validate_schematic(path, expected_netlist="")`
4. `simulate_schematic(path, timeout_s=60, include_data=false)`
5. `read_schematic(path)` — модель + предупреждения; неизвестные компоненты не роняют разбор.
6. `list_components()`
7. `describe_component(type)`
8. `open_schematic(path)` — запуск GUI отдельным процессом, не блокирует сервер.

Инкрементальные операции («добавь R2», «подвинь», «удали») — второй этап. В MVP правка = прочитать, изменить описание, перегенерировать с сохранением позиций.

Ошибки инструментов возвращаются структурированно (`error`, `detail`), без падения сервера.

## 16. Тесты

- Юнит (table-driven, `go test ./...`): парсер SPICE, нормализация значений, шаблоны `.sch`, преобразование выводов.
- Калибровка: полярность источников, диодов, BJT, MOSFET.
- Golden-схемы: RC-фильтр, делитель, диодный ограничитель, усилитель с общим эмиттером, MOSFET-ключ.
- Интеграция: генерация → нетлист → сравнение цепей; генерация → симуляция → ожидаемые значения.
- Регрессия: разобрать все `.sch` из `share/qucs-s/examples` без падений.
- Проверка отсутствия Qucs-S: тесты интеграции пропускаются, юнит-тесты работают.
- Ручная проверка: открыть 2–3 сгенерированные схемы в GUI (пользователь).

## 17. Риски и меры

| Риск | Мера |
|---|---|
| Неверные координаты/полярность выводов | калибровочные тесты + обязательная проверка нетлистом |
| Разные версии Qucs-S | фиксация шаблонов под 25.1.1, проверка версии, тесты |
| Метки не соединяются в GUI | проверено в нетлисте; ручная проверка в GUI |
| Ошибки симуляции при коде возврата 0 | проверять `.dat`, stderr, наличие переменных |
| Значения `M`/`MEG` | отдельная нормализация и тесты |
| Длинные пути и пробелы | `filepath`, список аргументов, `cmd.Dir` |
| Долгие симуляции | таймаут, структурированная ошибка |
| Потеря оформления при перегенерации | сохранять неизвестные секции и позиции по `ref` |
| Дрейф MCP SDK/протокола | версия SDK зафиксирована в `go.mod`; тесты инструментов через официальный клиент |

## 18. Мои решения (можно оспорить)

- **Go 1.27.3**, официальный MCP SDK v1.8.0, один бинарник `bin/qucs-mcp.exe`. Проект в `C:\Users\lau\Desktop\Soft\qucs-mcp`, отдельный git-репозиторий. Python не используем.
- Транспорт stdio.
- В MVP все связи — метками; провода только короткие выводы. Трассировка и шаблоны — второй этап.
- Диаграммы в `.sch` не генерируем; результаты доступны через `simulate_schematic`, графики — в Qucs-S.
- Источники — `S4Q_V`/`S4Q_I` с сырой SPICE-строкой; это закрывает DC+AC, SIN, PULSE, PWL.
- Подсхемы `X`/`Sub`/`Port` — второй этап; в MVP `X` даёт явную ошибку.
- Правка существующих схем в MVP — через `update_schematic`/`base_path`: перегенерация с сохранением позиций по `ref` и неизвестных секций. Инкрементальные операции — второй этап.
- Пробники `IProbe`/`VProbe` — второй этап. Напряжения узлов доступны и без них; токи при необходимости добавляются в GUI.
- `validate_schematic` без эталона проверяет генерацию нетлиста и структурные проблемы (висящие выводы, дубли `ref`, неизвестные компоненты), но не «неправильную, но самосогласованную» схему.
- `.include` разрешается относительно каталога `.sch`; отсутствие файла — ошибка проверки/симуляции.
- `open_schematic` — простой запуск GUI отдельным процессом; сервер его не ждёт.
- Нормализация значений — только для голых литералов; `{...}` и выражения не трогаем.
- Версия Qucs-S: если CLI работает — предупреждаем и продолжаем; если нет — понятная ошибка. Шаблоны зафиксированы под 25.1.1.
- `read_schematic` на неизвестных компонентах возвращает частичную модель + предупреждения, не падает.
- Безобидные директивы (`.end`, `.title`, `.options`, `.temp`, `+`) принимаются; `.end` молча, остальные с предупреждением.
