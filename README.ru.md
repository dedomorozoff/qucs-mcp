# qucs-mcp

MCP-сервер, который из SPICE-текста нетлиста собирает схему Qucs-S
(`.sch`), проверяет её реальным нетлистом, который генерирует сам Qucs-S, и
запускает симуляцию. Headless: `qucs-s` нужен только как subprocess.

```
SPICE-текст → internal/spice → model → internal/layout → .sch
           → qucs-s -n --ngspice → .cir → internal/netlist → internal/validate
           → qucs-s -n --ngspice --run → .dat → internal/dataset
```

Связность задают **метки проводов**, а не геометрия: одинаковые метки на
физически раздельных проводах сливаются в одну цепь, поэтому перестановка
компонентов никогда не меняет схему электрически.

## Сборка

```sh
go build -o bin/qucs-mcp.exe ./cmd/qucs-mcp
```

Бинарник отвечает на `--version` штампованной сборочной информацией — полезно
проверить перед отладкой регистрации в MCP:

```
$ bin/qucs-mcp.exe --version
qucs-mcp v0.2.0 (commit 1a4c918, go1.25.4, windows/amd64)
```

Нужны Go 1.25+ и локальная установка Qucs-S. Бинарник ищется в порядке:
`$QUCS_S_ROOT`, каталог `qucs/` рядом с репозиторием (или выше по дереву),
`PATH`, затем типовые системные каталоги установки. Первым зовите инструмент
`doctor` — он показывает, где именно искали.

## MCP-инструменты

| Инструмент | Назначение |
|---|---|
| `doctor` | проверка установки Qucs-S и конфигурации — звать первым |
| `create_schematic(netlist, name?, output_dir?, base_path?, validate=true, simulate=false, overwrite=false)` | SPICE-текст → `.sch`; возвращает `path`, `netlist_path`, `valid`, `report`, `warnings`, `simulation` |
| `update_schematic(path, netlist, validate?, simulate?)` | перегенерировать существующий `.sch` из нового SPICE-текста, сохранив позиции компонентов по ref |
| `validate_schematic(path, expected_netlist="")` | нетлист существующей схемы против её модели (или против явно заданного SPICE-текста) |
| `simulate_schematic(path, timeout_s?, include_data=false)` | симуляция; сводка датасета — имена переменных и число точек (`include_data=true` добавляет массивы) |
| `read_schematic(path)` | модель существующей схемы: компоненты (ref/type/value/x/y) + помеченные провода; неизвестные типы — предупреждения, не ошибки |
| `list_components()` | каталог поддерживаемых типов: R, C, L, S4Q_V, S4Q_I, DIODE_SPICE, _BJT, _MOSFET, GND, .AC, .TR, .DC, SpicePar, SpiceInclude, SpiceModel |
| `describe_component(type)` | детальный вход каталога: пины со смещениями, ориентация, пример строки схемы |
| `open_schematic(path)` | открыть схему в GUI qucs-s отдельным процессом (не блокирует сервер) |

Ошибки инструментов возвращаются структурированно: SDK отдаёт результат с
`IsError=true`, сервер продолжает работать.

## Регистрация в opencode

`~/.config/opencode/opencode.json` (или `%USERPROFILE%\.config\opencode\opencode.json`):

```json
{
  "mcp": {
    "qucs": {
      "type": "local",
      "command": ["C:\\path\\to\\qucs-mcp\\bin\\qucs-mcp.exe"],
      "enabled": true,
      "environment": {
        "QUCS_S_ROOT": "C:\\path\\to\\Qucs-S-26.1.1-win64"
      }
    }
  }
}
```

## Переменные окружения

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `QUCS_S_ROOT` | локальный `./qucs`, затем системная установка | корень Qucs-S |
| `QUCS_MCP_WORKDIR` | `~/Documents/qucs-mcp` | куда писать схемы, нетлисты и датасеты |
| `QUCS_MCP_TIMEOUT` | `120` | таймаут subprocess `qucs-s` в секундах |

## Семантика нетлиста

Эти правила и делают схему «целостной»; каждое покрыто интеграционным
тестом в `internal/e2e`.

- **Буквы приборов**: поддерживаются `R C L V I D Q M`. Всё остальное, и
  `.subckt`/`.ends` в частности, отвергается с сообщением, а не молча
  теряется.
- **`.model` карточки попадают в нетлист дословно**, вместе с точкой
  директивы: Qucs-S переносит их текст в `.cir` как есть.
- **Модели транзисторов — per device.** В spice-режиме Qucs-S строит
  `QMOD_<ref>` / `MMOD_<ref>` из свойств компонента, а не из именованной
  карточки, поэтому параметры карточки переносятся в прибор. PNP/NPN и
  PMOS/NMOS определяются по слову типа в карточке или по флагам
  `pchan`/`nchan`. Диоды по-прежнему ссылаются на карточку по имени.
- **Параметры без слота в свойствах Qucs-S сообщаются, а не теряются
  молча.** Параметры модели и экземпляра (включая `L`, `W`, `AREA`)
  раскладываются по номерным свойствам; всё немапленное (например, `THETA`
  из level-3) становится remark в результате.
- **Нет ни одной директивы анализа — считается постоянка.** Раньше схема без
  `.op`/`.ac`/`.tran` симулировалась в пустой датасет; теперь добавляется
  default operating point, и об этом пишется remark.
- **Пустой датасет — это ошибка, а не успех.** ngspice может прерваться
  (unespecified модель, плохая карточка), выйти с кодом 0 и оставить `.dat`
  только с осью развёртки. `simulate_schematic` сообщает об этом как об
  ошибке.
- **Имена цепей.** Цепь `gnd` (в любом написании) становится узлом `0`:
  Qucs-S разрешает её в землю, но продолжает печатать `v(gnd)`, и симуляция
  умирает. Имена узлов нечувствительны к регистру, поэтому `A` и `a` — одна
  цепь. Символы вне `[A-Za-z0-9_]` доживают до нетлиста, но исчезают из
  датасета, поэтому такая цепь переименовывается (`$n$1` → `_n_1`) и
  переименование попадает в warnings.
- **`.dc` развёртки недоступны** в spice-режиме Qucs-S: переменной развёртки
  нет, поэтому схема считается в одной точке постоянки, и инструмент честно
  об этом пишет в remarks.
- **Построчные комментарии `;`** вырезаются из своей строки и не попадают ни
  в значение, ни в имя цепи.

## Параллельность

Headless-запуски Qucs-S нельзя накладывать друг на друга. Два процесса
`qucs-s -n --ngspice`, стартовавшие близко по времени, подхватывают
промежуточный deck ngspice друг друга: в датасете остаётся анализ
запрошенной схемы, но **имена узлов из другой схемы** (воспроизводится на
Qucs-S 26.1.1 примерно на каждом третьем запуске). Поэтому сервер
последовательно выполняет все обращения к Qucs-S (`internal/runner`), и
параллельные `create_schematic`/`validate_schematic`/`simulate_schematic`
ждут своей очереди, а не гоняются. `internal/qtest` ради этого берёт
лок-файл — чтобы `go test ./...` оставался детерминированным между
пакетами.

Лок действует только внутри этого процесса. Не запускайте GUI Qucs-S,
второй экзепляр qucs-mcp или `qucs-s -n` руками на той же машине, пока
идёт симуляция: результаты могут оказаться от другой схемы. `open_schematic`
в очередь намеренно не входит — он только поднимает GUI.

Поведение страхует `internal/server/concurrency_test.go`: два клиента,
одновременно симулирующие разные делители, должны получить обратно именно
свои имена узлов.

## Откалиброванные особенности

- **Стоп-суффикс**: spice4qucs превращает Qucs `.AC` стоп `1M` в ngspice
  `1m` (мега тихо теряется, sweep укорачивается). Layout пишет start/stop
  суффикс-свободной научной формой (`1e+06`) — проверено на 10 Hz → 1 MHz,
  456 точек.
- В SPICE-тексте `1M` = **милли**; мега — `1MEG`/`10MEG`. Нормализация
  значений переводит между конвенциями SPICE и Qucs, включая суффиксно-цифровые
  литералы (`3k3` = 3.3k, `4R7` = 4.7).
- Точек в log-развёртке Qucs: `round(точек_на_декаду × декад) + 1`; в
  переходном процессе: `round((stop − start) / step) + 1`.
- Калибровка пинов: у `S4Q_V`/`S4Q_I` с `mirror=0` пин 1 («+») в (+30, 0);
  у вертикальных пассивов с `Rot=3` пин 1 сверху; у `_BJT` пины C, B, E, у
  `_MOSFET` — D, G, S с bulk, сведённым в source. Провод соединяется с пином
  только концом, точно стоящим на пине.

## Тесты

```sh
go test ./... -timeout 300s
```

Юнит-тесты работают везде. Интеграционные (`internal/e2e`,
`internal/validate`, `internal/dataset`, `internal/server`) зовут настоящий
`qucs-s` и пропускаются, если он не установлен. Регрессия читалки
прогоняется по всем `.sch` из `qucs/share/qucs-s/examples` (248 файлов).

## CI

`.github/workflows/ci.yml` собирает и тестирует на Ubuntu и Windows:
`gofmt`, `go vet`, `go build`, `go test` и релизный бинарник в артефактах.
Без Qucs-S на раннере интеграционные тесты пропускаются, но юнит-сьют всё
равно gating.

## Релизы

`.github/workflows/release.yml` стартует по тегу `v*`: кросс-компиляция
windows/linux/darwin × amd64/arm64, упаковка каждого в
`qucs-mcp-<tag>-<os>-<arch>.(zip|tar.gz)` рядом с копией этого README,
`SHA256SUMS` и публикация GitHub Release с сгенерированными заметками.
Версия и коммит штамуются в бинарник через `-ldflags -X`, поэтому скачанный
билд сообщает тот тег, из которого он собран.

```sh
git tag -a v0.2.0 -m "coherent schematics" && git push origin v0.2.0
```

Используются только first-party действия и встроенный в раннер `gh`;
сборку бинарников гейтит job `checks` (gofmt, vet, build, test). При этом
интеграционные тесты с Qucs-S на раннере без Qucs-S всё равно пропускаются,
так что числовое поведение по-прежнему гейтится CI на раннере с реальным
`QUCS_S_ROOT`.
